# vdom 标准理论（终态等价理论）与根本性修复计划

> 方法（用户决策 2026-XX）：**先建立标准理论 → 用可执行验证证明理论能
> 抓住整类 bug → 按理论优化代码 → 最后改造测试**。
> 已完成的实证：命令流模拟器 + 终态对账 + 模糊测试——4/4 已知缺口 +
> **1000 对随机树 93 个终态不等价（9.3%）**——证明现有实现不满足理论，
> 也证明理论验证能抓住存在性测试免疫的 bug 类。

---

## 1. 工作流程全景（理论的对象）

```
vnode 树（纯数据——type/props/key/children）
  ├─ build：首帧/整树替换 → 全量命令流（create/insert/close/done.full）
  ├─ diff： 有影子树 → 增量命令流（对照旧树——精准 patch）
  └─ 组件：两阶段（工厂=mount 一次；renderFn=每次渲染——输出经 sink 递归）
        ↓
命令流（NDJSON 可序列化——13 种 op——函数经 $fn 表）
        ↓
patch 消费（CommandApplier——幂等——对齐现有 DOM）
        ↓
三重状态（**完整终态**）：
  S_DOM —— DOM 树结构（childNodes 槽位序列——同构不变量）
  S_EVT —— 事件表（id → event → handler——事件代理）
  S_INST —— 组件实例注册表（compId → { renderFn, onUnmounts, lastOutput, hooks }）
```

**核心洞察**：引擎的"状态"不是 DOM 一个面，而是三个面。历史上所有
残留类 bug 都是**三个面不同步**：DOM 残留（G2/G3/G7）、事件表残留（G4）、
实例表残留（G5/G8）。测试只断言命令流"存在性"（有 remove 命令？），
从不断言**三面终态**与目标一致——这是 9.3% 不等价率的根本原因。

## 2. 标准理论（公理 + 定理）

### 定义

- **投影（Projection）**：vnode 树 → 目标终态三面（DOM 结构/事件表/实例表）
  的确定性函数 `project(tree)`。DOM 面按槽位展开（childrenOf 单一规则源——
  空洞=0 宽锚——keyed 项位置无关但 DOM 有确定位置）。
- **完整终态**：`state = (S_DOM, S_EVT, S_INST)`——三面合称。
- **命令流消费**：`consume(cmds, s0) → s1`——patch 语义的确定性执行
  （模拟器 = 该语义的纯数据实现——与浏览器 proc* 对齐）。

### 定理 1（终态等价——diff 正确性的判据）

```
∀ oldTree, newTree, s0 = consume(build(oldTree), ∅)：
    consume(diff(oldTree, newTree), s0) ≡ consume(build(newTree), ∅)
```

即：**diff 的增量路径必须与 build 的全量路径收敛到同一终态**。
- 推论 1.1：diff 的任何实现错误（漏 remove/漏 unmount/漏事件解绑/错位置）
  ⟹ 终态不等价 ⟹ 可被机器对账捕获。**反之，对账零报错 = 无 diff 错误**。
- 推论 1.2：命令流可被部分/重复消费（幂等）——终态仍收敛（自愈前提）。

### 定理 2（区间投影——结构正确性的判据）

```
∀ vnode 槽位序列 cs（childrenOf 展开后）：
    |S_DOM.childNodes| == |cs|     （占位法——空洞有 0 宽锚）
    ∀i: kindOf(cs[i]) == 槽位 i 的 DOM 节点形态   （元素/文本/锚——同构）
```

- 推论 2.1：**id = 槽位路径**（pathId——唯一命名体系——零特判）；
  组件输出挂槽位 id（锚点法）——组件占位锚 = 首槽位 id。
- 推论 2.2：**区间语义**——组件/Fragment 输出多根 = 连续槽位区间——
  移除必须按区间（全槽位 remove + 区间内实例 unmount）——任何"单锚 remove"
  都是违例。
- 推论 2.3：嵌套组件实例 id ⊆ 其区间槽位 id（compId.0 特判是**命名空间
  违例**——必须消除或规则化）。

### 定理 3（生命周期同构——资源正确性的判据）

```
∀ 组件实例 i：i 存活 ⟺ i 的区间在 S_DOM 中存在
```

- 推论 3.1：**卸载唯一入口** = 区间移除消费（remove 语义携带区间实例集）
  ——diff 分支不再逐个发 unmount（发射点收敛——遗漏类 bug 结构性消灭）。
- 推论 3.2：事件表条目存活 ⟺ 新树投影含该 (id, event) 绑定（对称性——
  见定理 4）。

### 定理 4（差集对称——diff 完备性的判据）

```
diff(old, new) 必须覆盖两个方向 × 所有面：
  新有旧无（增/改） + 旧有新无（删/解绑）
  面：静态属性 / 事件函数 / ref / 实例
```

- 推论 4.1：任一面对任一方向遗漏 ⟹ 终态不等价（G4 是"函数面旧有新无"
  方向遗漏——静态面已对称、函数面不对称——结构性违例）。

### 定理 5（幂等收敛——健壮性的判据）

```
∀ 命令流 cmds（同一目标的任意前缀/重复）：
    consume(cmds; consume(cmds, s0)) ≡ consume(cmds, s0)
```

- 推论 5.1：渲染错误/回退后重跑全量 build 自愈（serve 已有此设计——
  理论化并纳入校验）。

## 7. 风险与边界（诚实裁剪）

- **模拟器 ≠ 浏览器**：proc* 语义对齐是模拟器可信度前提——模拟器与
  proc* 的差异（如 insert 细节）可能漏抓 patch 层 bug——场景层真实 DOM
  对账兜底（双层验证）
- **fuzz 树形态**：组件树 fuzz 覆盖有限（工厂副作用/状态/异步 renderFn
  不随机化）——组件专项用例人工维护
- **事件表对账的粒度**：handler 引用不可序列化——对账比较 (id, event)
  键集存在性 + 移除方向——"handler 换成错误函数"不抓（函数面引用比较
  已有 diffAttrs 契约测试）
- **不改动**：渲染队列/redirect（已知边界）、keyed 循环移位决策、
  SSR 吸收策略——保持现状由场景层覆盖

## 9. 诊断：定义缺失层（为什么定义清晰仍有 bug——四个理论原因）

> 问题（用户 2026-XX）：vdom 流程定义清晰（vnode → build/diff → 命令流 →
> patch → DOM——文档/注释/设计规则齐全），但实现仍反复出 bug——需要从
> 理论上找到原因。

**核心论断**：定义的清晰性在「流程步骤」（做什么），不在「不变量」（什么
必须始终成立）——vdom 定义缺少不变量层。不变量是隐含承诺，散落在几十个
函数的隐性契约里，没有任何一处代码持有它。这不是写错的问题——是**定义
本身缺了一层**。

### 9.1 原因 1：投影维度不一致——定义假设 1:1，流程存在 1:N

定义的 id 体系建立在「1 vnode ⟷ 1 id ⟷ 1 DOM 节点」（pathId(parent, index)）。
但流程存在**多值投影**：Fragment 展开、组件输出数组——声明世界 1 个槽位
→ 命令世界 N 个命令 → DOM 世界 N 个兄弟节点。1:N 在定义中不存在——实现
靠特判（outIsComponent 的 compId.0、transitionComponent 单锚 remove）——
**每个特判都是新 bug 源**。

证据：id 冲突（组件输出数组 root.0.1 被兄弟 button 抢占——build 命令流实证）、
G2/G7（区间只清首锚）。

**补救**：定义显式区分「单值投影」与「区间投影」——区间一等化（id 按区间
分配、remove 按区间消费——removeInterval 唯一入口）。

### 9.2 原因 2：不变量无持有者——宣称有，实例化无

定义说「占位法保长度恒定」「实例存活 ⟺ 区间存在」——但没有任何函数检查
长度恒定（createAnchor/remove/insert 的隐性契约）、没有代码持有生命周期
不变量（unmount 发射点 5 个分支各自为政）、没有测试断言终态（只有命令
存在性断言——「有 remove 命令」≠「区间清干净了」）。

**不变量没有持有者 = 没有人对它负责 = 每次修改都可能破坏它而无人知晓**——
88/1000 fuzz 反例的根本原因。

**补救**：不变量实例化为可执行检查（对账器 = 不变量持有者——三面对账 + fuzz）。

### 9.3 原因 3：递归上下文隐式化——定义未描述，实现手工传递

定义的流程是线性（命令流），实现是递归树遍历。递归之间传递的上下文
（ref/lastRef/index/compId）在定义中不存在——实现的隐式状态。**每个递归
调用点都要手工维护上下文——每个维护点都是 bug 候选**（lastRef 在 fragment
展开不更新——顺序语义靠 unshift 兜底；index+i 在组件输出数组——id 冲突；
compId.0 特判——命名空间违例）。

**补救**：上下文内化为唯一入口（removeInterval/emitWithKey 收敛——调用点
不再手工算 ref/id/区间）。

### 9.4 原因 4：单帧定义 vs 多帧正确性——定义盲区 = bug 高发区

流程定义描述单次渲染（一帧）。vdom 本质是跨帧增量——正确性全在帧间：
影子树（旧帧）、组件注册表（跨帧实例）、事件表（跨帧绑定）与 DOM 的
一致。G4（事件表残留）、G5/G8（实例泄漏）、G1（旧帧 lastOutput 数组）——
全部是帧间 bug。单帧视角的代码无法保证多帧不变量——除非不变量被实例化。

**补救**：帧间不变量实例化（S_EVT/S_INST 入终态——对账器天然跨帧）。

### 9.5 汇总

| 原因 | 本质 | 补救 | 消灭的 bug |
| --- | --- | --- | --- |
| 投影维度不一致 | 定义假设 1:1，流程存在 1:N | 区间一等化（removeInterval 唯一入口 + id 空间分离） | G2/G7 + id 冲突 |
| 不变量无持有者 | 宣称有，实例化无 | 对账器 = 不变量持有者（三面对账 + fuzz） | G3/G5/G8 + fuzz 全族 |
| 上下文隐式化 | 定义未描述，手工传递 | 上下文内化（唯一入口收敛） | G1 + insert 顺序类 |
| 单帧 vs 多帧 | 定义盲区 = bug 高发区 | 帧间不变量实例化（S_EVT/S_INST 入终态） | G4 + 残留类 |

**结论**：修 bug 模式永远修不完——每次修的是实例（某个分支漏了 unmount），
不是原因（unmount 无持有者、无实例化检查）。原因在定义之外——直到不变量
被实例化（对账器）或上下文被内化（唯一入口）。

## 10. 验证策略选型：为什么不需要新语言

> 讨论记录（用户 2026-XX）：纯函数式语言（编译到 TS）/ 领域 DSL 保证 vdom
> 健壮性的可行性分析——结论：不需要新语言范式，TS 三层体系已覆盖。

### 10.1 bug 分类 × 语言特性匹配（决定性论据）

G1-G8 逐一分类：7/8 是**纯函数内部的逻辑错误**（区间不完备/单向 diff/
unmount 遗漏/id 冲突）——纯度、ADT、不可变性等纯函数式语言特性全部不防；
仅 G1（空值访问）是类型级（TS 的 ADT 同样能防）。**纯函数式是必要条件
不是充分条件**——静态防逻辑错误需要依赖类型/细化类型（Agda/Idris/Liquid
Haskell 级别）——那是证明助手，不是纯函数式。

### 10.2 编译到 TS 的工程现实

- 技术可行（Elm/PureScript/Fable 先例——Elm 用 Elm 写自己的 vdom，仍有
  bug 史——语言纯度没消灭逻辑错误——实证）
- 互操作边界是最大的洞：组件工厂/renderFn（TS 用户代码）、patch 层（本质
  不纯）、hooks/事件、函数面传输——跨语言调用时 id 空间/区间不变量全部丢失
- 调试断层 + 编译器自身是新 bug 源 + 团队认知成本

### 10.3 结论：TS 三层体系等价于语言级方案

| 语言级（依赖类型） | TS 三层体系 | 差距 |
| --- | --- | --- |
| 编译期检查 | CI 期检查（fuzz 常驻——核心模块 CI 必过才部署） | 时机差异——实际小 |
| 类型内建不变量 | 品牌类型 + 唯一 API（架构约束——合法错误不可表达） | 同效果 |
| 证明 | 对账 = 可执行证明（consume 确定性 ⟹ 错必被抓——演绎部分相同） | 归纳部分靠 fuzz 采样（已实证 88/1000） |

**问题不是「语言不够强」，而是「定义缺了不变量层」**——补上这一层
（对账器/唯一入口/类型分离），TS 完全承载。
