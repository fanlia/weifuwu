# Sandbox 集群化方案（基于三端事件流——2026-12——执行状态：未开始）

> 背景：单宿主 sandbox（manager + docker 同机）——1000 部门规模需要多宿主。
> 三端事件流（vdom + ai + sandbox 统一模型）是集群化的**神经系统**：
> 各宿主的状态/动作全部事件化——中心基于事件流做调度/检测/聚合——
> 不是轮询（事件驱动 vs 定时扫描——之前的架构分水岭）。
>
> 核心洞察：
> - **事件流聚合 = 集群的统一状态视图**（各宿主 exec/生命周期事件上报中心——
>   容量/负载/活跃度从事件流推导）
> - **requestId 跨宿主链**（一次任务的执行路径——AI 决策（中心）→ 沙盒执行
>   （某宿主）——requestId 贯通——精确因果跨宿主）
> - **事件驱动调度**（exec:start/end 聚合——宿主活跃度——新沙盒路由到最空闲）

---

## 一、架构

```
┌─────────────────────────── 中心（控制面——已有 server + DB） ───────────────────────────┐
│  事件流聚合（各宿主上报——统一缓冲——/api/events 跨宿主查询）                              │
│  集群调度器（基于聚合事件流——沙盒创建路由——负载均衡——配额）                              │
│  集群 reconcile（DB 期望 vs 各宿主实际——漂移跨宿主检测——宿主心跳超时判定）                │
└─────────────────────────────────────────────────────────────────────────────────────┘
        │ ws/HTTP（事件上报——统一 schema { entity:'sandbox', action, target, payload{host} }）
┌───────┴───────┐      ┌───────────────┐      ┌───────────────┐
│ 宿主 1        │      │ 宿主 2        │      │ 宿主 N        │
│ sandbox-host  │      │ sandbox-host  │      │ sandbox-host  │
│（docker 执行器│      │（docker 执行器│      │（docker 执行器│
│ + 本地事件发射）│      │ + 本地事件发射）│      │ + 本地事件发射）│
└───────────────┘      └───────────────┘      └───────────────┘
```

## 二、组件拆分（基于现有 sandbox 层）

### 2.1 宿主执行器（可拆分边界——现状已就绪）

```
现有：manager.ts（状态机/调度）+ docker.ts（执行器）——同进程
集群：docker.ts 拆为"宿主执行器"（每宿主一个 sandbox-host 进程）——
      manager.ts 留中心（DB 状态 + 调度 + reconcile——调远程宿主）
```

- `DockerSandbox`（docker.ts——ensure/exec/stop/dispose——**已是独立执行器**）——
  作为宿主执行器的实现——加**宿主身份**（hostId——事件 payload 带）
- 宿主接口（`SandboxHost`）：`ensure/runTool/stop/dispose/isBusy/status`——
  本地实现（当前 docker）+ 远程实现（中心 → 宿主 RPC——HTTP/ws）

### 2.2 宿主进程（sandbox-host）

```
新进程（每宿主部署）：加载 DockerSandbox + 事件发射——注册中心（ws 连接）
  → sandbox:host:register（事件——hostId/容量/镜像）
  → 接收中心指令（ensure/exec/stop——RPC）
  → 执行 + 发射事件（sandbox:exec:start/end——payload 带 hostId）
  → 心跳（exec 事件即心跳——活跃证明）
```

### 2.3 事件上报（宿主 → 中心）

```
统一 schema（三端标准）：{ entity:'sandbox', action, target, payload{ hostId, ... }, ts }
传输：ws（实时——宿主与中心长连接——事件流式上报）
聚合：中心环形缓冲（跨宿主统一——查询 API 加 host 过滤）
持久化：sandbox_events 表加 host_id 字段（跨宿主历史审计）
```

## 三、关键设计（基于事件流）

### 3.1 沙盒路由（创建时选宿主——容量视图）

```
调度器订阅各宿主事件（exec:start/end + 心跳）——维护"宿主活跃度"：
  hostLoad = Σ(运行中 exec) + Σ(容器内存)（从事件流推导——不是轮询）
创建沙盒 → 路由到负载最低的宿主（事件驱动视图——实时）
约束：部门配额（已有）——镜像可用性（宿主本地镜像/拉取）
```

### 3.2 亲和性与工作目录（关键决策）

| 方案 | 工作目录 | 路由 | 故障转移 |
|---|---|---|---|
| **A 宿主亲和**（部门绑定宿主） | 宿主本地磁盘（现状） | 部门首次创建 → 固定宿主 | 宿主宕机 → 沙盒 error（工作目录不可达）——部门重建到新宿主（数据迁移手动） |
| **B 共享存储**（NFS/对象） | 共享（跨宿主） | 任意宿主（负载均衡） | 宿主宕机 → 沙盒重建到其他宿主（工作目录保留——自动恢复） |

**建议**：阶段 1 用 A（现状零存储改动——亲和路由）——B（共享存储）为规模化
终态（复杂——存储基建）。

### 3.3 故障检测与恢复（事件驱动）

```
宿主心跳：exec 事件 + 定时 ping（30s）——中心超时（90s）→ sandbox:host:down（事件）
恢复：
  - A 亲和：宿主 down → 其沙盒标记 error（事件）——恢复后 reconcile 重建
  - B 共享：宿主 down → 沙盒自动迁移（重建到其他宿主——工作目录保留）
执行中的任务：exec 中断 → ai 事件流可见（requestId 链断——AI 重试）
```

### 3.4 集群 reconcile

```
中心：DB 期望状态（全宿主）vs 各宿主上报的实际（事件流推导——各宿主容器列表
      定期上报）——漂移检测（跨宿主——sandbox:reconcile:drift——host 维度）
现有 reconcile 的集群版：单宿主扫描 → 按宿主分片（每宿主独立 reconcile——
中心聚合统计）
```

### 3.5 requestId 跨宿主链

```
一次任务：AI 决策（中心）→ 工具调用 → exec（宿主 A）——requestId 贯通——
统一查询 /api/events?requestId= 聚合宿主 A 的事件（事件上报带 requestId——
跨宿主聚合——一次任务的执行路径（在哪个宿主执行——耗时——全链路）
```

## 四、实施路径（渐进——基于事件流基础）

```
阶段 1：宿主抽象（SandboxHost 接口——DockerSandbox 实现 + hostId 事件标注）
阶段 2：宿主进程（sandbox-host——注册中心 + 事件上报（ws）——中心聚合缓冲）
阶段 3：集群调度器（事件流容量视图——创建路由（亲和 A 方案））
阶段 4：集群 reconcile + 故障检测（心跳 + 漂移跨宿主）
阶段 5：（可选）共享存储（B 方案——迁移/自动恢复）
```

## 五、测试与验收

- 阶段 1：宿主接口抽象（本地实现——现有测试全绿）
- 阶段 2：宿主注册/事件上报（mock 宿主——中心聚合——host 过滤查询）
- 阶段 3：路由（两宿主负载视图——新沙盒到最空闲——事件断言）
- 阶段 4：心跳超时（宿主 down → 事件 + 沙盒标记）——reconcile 分片
- 每阶段独立提交可回滚

## 六、风险与裁剪

| 项 | 风险 | 缓解 |
|---|---|---|
| 事件传输断 | ws 断 → 宿主操作不可见 | 重连 + 本地缓冲重放——reconcile 兜底 |
| 宿主状态不一致 | 事件丢失/延迟 | 事件 + reconcile 双源校验（已有哲学） |
| 亲和路由的负载不均 | 部门绑定宿主——冷热不均 | 事件流容量视图——新部门路由 + 手动迁移 |
| 共享存储 | 基建复杂（NFS/对象） | 阶段 5（裁剪——先亲和方案） |
