## 一、现状审计（诚实告知——已有成熟交付）

**该场景平台已有一整套「AI 真填档」交付（2026-12 新架构）：**

| 件 | 位置 | 说明 |
| --- | --- | --- |
| 10 人设种子 | `scripts/seed-survey-agents.mjs` | 财务小王/市场小李/产品老张/客服小陈/研发大刘/人事小周/销售阿强/运营小赵/行政陈姐/实习生阿泽——各独立部门（独立沙盒并发）——人设 prompt（年龄/态度/评分倾向/语气） |
| 一键派单 | `POST /demo-survey/launch` | 服务端并发派单（BATCH=3 · 批间 10s——连接池/容器启动峰值控制——45s 池满事故防线）——@角色 触发——`{ success, sent, roles }` |
| 角色填写链 | agent-browser（沙盒内） | open 问卷 → snapshot 读题 → fill/select/check 作答 → submit → 结果写工作目录 `survey-result.json`（交付物）→ close |
| 实时统计 | `/demo-survey/stats` + WS `/survey-live` | 逐题答案流/提交计数/在线数/来源列表——统计页实时跳动 |
| 生产验收 | `scripts/survey-acceptance.mjs` | 终态断言：10 提交 + 在线归零（10 分钟超时） |
| 辅助 | survey-launch / survey-summary / survey-demo | 派单/汇总/演示辅助 |

**缺口（本轮需求的落点）：**

1. **无轻量确定性档**——模拟 = 只能用 AI 真填（LLM + 沙盒 + 浏览器——10 分钟级——每次 10 容器 + 10 × LLM 调用——**演示节奏重 / 有成本 / 不可控**）
2. **验收依赖 LLM**——角色答错/卡住 → 超时失败——**不可作问卷系统的 CI 回归**（问卷本身改动的验收被 AI 不确定性绑架）
3. **可重复性弱**——同 seed 不同次答案漂移（LLM 采样）——数据生成不可复现

**协议面勘查结论（模拟器可行性）**：WS `/survey-live` 为完整协议面（`survey:hello/answer/submit/bye` + 服务端广播 `state/online/submitted`）——**无来源唯一性校验**（source 即字符串标识）——**协议级客户端可直接完成全部交互**——统计页/验收脚本的观测面对模拟器同样成立。

## 三b、1000 规模化专篇（A 档——sandbox 管理为核心——2027-09 审计）

### 需求定型（先分清三态——架构决策分叉）

| 形态 | 语义 | 单机可行性 | 结论 |
| --- | --- | --- | --- |
| **分批型** | 1000 角色分批执行——统计页累积到 1000 | ✅ 20-60 并发 | **推荐目标**（1-2 小时完成——统计分布是产出） |
| **高吞吐型** | 时间压缩（演示节奏） | ✅ 大内存机（64GB→60 容器） | 配置增强（池预算/并发闸刻度） |
| **全并发型** | 1000 角色同时在线填写 | ❌ 需集群（1000×1GB≈1TB） | **暂缓**（真多宿主 RPC 执行=阶段 4 大工程——需求真到再立项） |

**资源数学（分批型）**：20 并发 × 90s/角色 ≈ 800 角色/小时——1000 ≈ 75 分钟
（含 LLM/浏览器/提交——10 角色实测节奏推算）——主机内存 = 池预算上限
（10240MB 默认=10 容器——提升需 SANDBOX_POOL_BUDGET_MB + 物理内存）——
**单机方案成立——集群不是 1000 的充要条件**。

### sandbox 管理问题清单（已审计——按严重度排序）

| # | 问题 | 证据 | 规模冲击（10→1000） | 修法 |
| --- | --- | --- | --- | --- |
| P0-1 | **无等待队列**——池满 → `queue:rejected` 抛错 | manager.ts ensurePoolBudget（驱逐 LRU→仍超→throw） | 1000 时必然拒绝——角色答题失败（非排队） | exec 排队（池空位即跑——超时可见——busy 豁免保持） |
| P0-2 | **派单批控硬编码** | launch BATCH=3/批间 10s | 1000/3×10s = 55 分钟纯派单 | 池容量感知滑窗（按剩余容器自适应批次） |
| P1-1 | **任务级资源保护缺位** | LRU 驱逐按 last_used_at——LLM 思考间隙容器 idle | 批处理下驱逐窗口放大（长任务被回收） | 会话活跃容器豁免（agent 任务期 protected 标记） |
| P1-2 | **批量收尾缺失** | idle 10min → stop；stop 24h → terminate | 1000 角色跑完 → 1000 容器空转 10min | 任务完成信号 → 批量回收（省资源/回收可观测） |
| P1-3 | **统计页 1000 展示** | 逐来源进度列表（progress map 全量） | 1000 行列表爆——统计意义丢失 | 聚合分布（年龄段/行业/评分直方图——1000 的价值） |
| P2-1 | **容器启动风暴** | docker 并发启动无节流 | 批切换时 20+ 容器同起 | 预热池（keep-N 冷容器——冷启动隐藏） |
| P2-2 | **1000 人设供给** | seed 硬编码 10 角色 | 1000 需矩阵生成 | seed --count（行业×职级×性格矩阵——批建事务） |
| P2-3 | **可观测** | 状态计数有（statusCounts）——拒绝/失败无告警 | 1000 失败不可见 | metrics 池使用率/拒绝数/失败率 + 任务级看板 |
| P2-4 | **LLM 上游并发** | 单 key 配置（settings BYOK）——并发闸未见 | 1000 并发 SSE 上限未探明 | LLM 并发闸（与沙盒池联动背压——**诚实标注：未知面——执行前需实测**） |
| P2-5 | **DB 批建** | seed 循环建部门/agent | 1000 行批建——长事务/锁 | 分批事务（每 50 一批——进度可见） |

## 三c、Campaign 架构设计（第一个客户交付——总量/并发可配置）

### 需求定型（客户确认）
- **分批型 = 生产语义**——但**总量与并发可配置**（总量多少、同时在线多少——
  客户参数而非硬编码）
- 第一个客户：`--total=1000 --concurrency=30` 形态——**CLI 驱动 + 脚本面独立**
  （服务端零改动优先——管理 UI 后置——客户是平台 owner 团队）

### 设计决策：Campaign 运行器（scripts/survey-run.mjs——核心新增）

```
node --env-file=.env scripts/survey-run.mjs
  --total=1000         # 角色总量（从人设池取——默认全池）
  --concurrency=30     # 同时在线上限（水位滑窗——显式客户配置）
  --pace=1.2s          # 补派间隔（容器启动错峰）
  --timeout=180s       # 单角色完成超时（派单→提交）
  --retry=2            # 失败重试次数（超时/拒绝→重派）
  --checkpoint=run.json # 断点续跑（中断零重来）
  --matrix=10x10x10    # 人设矩阵（未 seed 时自动生成）
```

**调度循环（水位滑窗——不是一次性全派）**：
```
角色池 = 人设池 - completed - failures（checkpoint 恢复）
在线 = {}（角色 → 派单时间）
loop:
  ① 水位补派：while 在线数 < concurrency 且 池有未派角色
     → POST 部门消息（@角色——触发填写——现有派单面）
  ② 完成扫描（5s）：轮询部门文件 API——survey-result.json 出现 = 完成
     → completed++ / checkpoint 落盘（每 10 个）
  ③ 超时处理：在线角色 超 --timeout → 失败 → retry 内重派 → 失败清单
  ④ 终止：completed + failures(重试耗尽) >= total → 汇总退出
产出：summary（分布/失败/耗时）+ 失败清单（重跑命令）
```

**三层并发闸（取最小 = 有效并发）**：
| 闸 | 上限 | 来源 |
| --- | --- | --- |
| 沙盒池容器数 | 池预算/物理内存（50 并发=64GB 机器） | env SANDBOX_POOL_BUDGET_MB |
| LLM 上游 | **诚实标注：未知面**——单 key 并发未实测 | 试点 100 测量后定（多 key 轮换备选） |
| 派单窗口 | --concurrency（客户显式） | CLI 参数 |

**关键选型**：
- **完成信号 = 文件轮询**（survey-launch --watch 现有模式——5s×1 请求——
  简单可靠——不新增 WS 依赖）——WS file_updated 订阅留作优化候选
- **agent 触发面不变**（部门消息 @角色——seed 已建的角色部门——零服务端改动）
- **checkpoint 断点续跑**（1000 跑 ~1.5h——中断不重来——客户可接受的关键）
- **人设矩阵**（seed --count/--matrix 参数化——行业×职级×性格——
  prompt 模板化生成——指令遵循稳定性）

### 服务端改动最小面（诚实评估）
| 改 | 必要性 |
| --- | --- |
| seed-survey-agents.mjs 参数化（--count/--matrix——批建事务） | **必需**（1000 人设供给） |
| launch API 参数化（角色集） | **不必需**（脚本直发消息——survey-launch 已证） |
| 统计页聚合分布 | **必需**（1000 的产出面——S4） |
| 沙盒服务端 | **零改动**（水位脚本控制——池预算 env 刻度） |
| WS/消息/agent 面 | **零改动**（现有机制全复用） |

### 交付时间线（分阶段爬坡——数据驱动）
1. **试点 100**（~10 分钟）：seed 100（矩阵 4×5×5）→ 100 跑通——**测量**
   （LLM 并发/失败率/单角色成本——定 --concurrency 与 retry）
2. **生产 1000**（~1.5 小时）：全量跑——失败清单重跑收尾——分布产出
3. **观测面**：统计页聚合（S4）——分布/完成率/失败率——客户交付报告

### 风险清单（第一个客户）
- **LLM 上游限流**（试点 100 实测——失败模式面——多 key 轮换备选）
- **人设 prompt 漂移**（矩阵模板化——稳定句式——指令遵循测试）
- **问卷版本变化**（角色步骤失效——版本号进 prompt——问卷变更重 seed）
- **成本**（1000 × ~8 次 LLM——试点 100 先测量再承诺）
- **沙盒泄漏**（reconcile/驱逐已备——量级放大后监控池使用率）
