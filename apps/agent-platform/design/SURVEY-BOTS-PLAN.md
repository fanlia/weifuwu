# SURVEY-BOTS-PLAN · 完整方案 v2（2027-09 实测校准版）

> **场景**：模拟机器人填写问卷——10 测试 → 100 试点 → **1000 生产**——
> **AI 真实填写档**（LLM + 沙盒 + agent-browser——不是协议模拟器）。
> **产品使用方式**：用户**在部门聊天框输入**（自然语言）——AI 干活、
> 进度可见、失败可续——**脚本/API 均为工程面（不进产品叙事）**。
>
> **v2 修订（2027-09——试点实测校准——替代 v1 的预估模型）**：
> 单角色真填 **45s**（v1 预估 4-5 分钟——**5× 乐观**）；试点 100 实测
> **5.3 分钟**（concurrency=10——**0 失败**）；数据分布健康（人设映射
> 生效）；sandbox 配额实测 **306MB/容器**（v1 按 500MB 高估——512MB
> 配额 → 20 并发）；S3 等待队列**正式判负**（水位反馈替代——调度器
> 查池现状降窗，不拒绝）。

## 二、产品形态（用户视角一条线——不变）

```
用户在部门聊天框
  ├─ 小批量（10-50 ≤ 池）：@全员/@角色 「请大家填写问卷」
  └─ 大批量（100-1000）：「@问卷助手 让 1000 人填问卷，同时 20 人」
       ① 助手解析意图（总量/并发/链接）→ 调调度器工具
       ② 水位派单（不是 @全员）→ 聊天流进度「320/1000 · 失败 2 · 重试中…」
       ③ 用户可续：「重跑失败的」
```

**心智统一**：小批/大批都是「跟 AI 说话」——角色池、批次、沙盒、
并发对用户不可见——launch API / 运行器 = 工程面（不宣传不修正）。

## 三、实测校准的性能模型（v2 核心修订）

### 3.0 实测数据（2027-09——全部真实验证）

| 参数 | 实测值 | 来源 |
| --- | --- | --- |
| 单角色端到端 | **45s**（读消息→agent-browser 开页→填 5 题→提交→写结果→完成信号） | 单角色 campaign |
| 试点 100 | **5.3 分钟**（concurrency=10——100/100、0 失败） | S7 试点 |
| 容器内存 | **306MB**（问卷页——chromium 满载） | docker stats |
| 容器启动 | **<1s**（docker run 秒回） | 实测 |
| 任务内 exec 链 | 每角色 ~10-15 次工具调用 | 压测 800 次（68ms/次） |
| LLM 调用 | ~8-10 次/角色（快照→决策→工具） | 观察 |

### 3.0.1 新性能模型

```
1000 生产 = 1000 × 45s / K 并发（K = min(客户并发, 池容量, LLM 上游闸))
  K=10 → ~75 分钟    K=20 → ~37.5 分钟（512MB 配额——沙盒池翻倍）
```

**关键修订**：v1 的 1.5 小时预估建立在「4-5 分钟/角色」（LLM 慢速假设）——
实测 45s 后**瓶颈不在速度为 LLM 轮次，而在并发闸**（池容量 10→20 翻倍
是最大杠杆——配额降配 512MB——实测 306MB + 30% 余量）。

**并发闸优先序**（取最小 = 有效并发）：
1. **沙盒池**：池预算 10240MB ÷ 512MB = **20 容器**（v1 按 1024MB = 10）
2. **LLM 上游**：10 并发实测无限流——**20 并发未实测**（S7b 必须先测）
3. **客户 --concurrency**：用户参数
