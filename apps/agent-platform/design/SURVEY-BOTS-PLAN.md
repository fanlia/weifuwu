# SURVEY-BOTS-PLAN · 完整方案（2027-09 终稿）

> **场景**：模拟机器人填写问卷——10 个为测试阶段，**生产 1000 个**——
> **AI 真实填写档**（LLM + 沙盒 + agent-browser——不是协议模拟器）。
> **产品使用方式**：用户**在部门聊天框输入**（自然语言）——AI 干活、
> 进度可见、失败可续——**脚本/API 均为工程面（不进产品叙事）**。
> **形态确认**：分批型 = 生产语义——**总量/并发可配置**（客户参数）。

---

## 一、需求定型

| 项 | 定论 |
| --- | --- |
| 机器人 | AI 角色（人设 agent——LLM 驱动真实填写——非模拟器） |
| 规模 | 10（测试）→ 100（试点）→ 1000（生产）——分批执行 |
| 可配置 | 总量 N（100-1000+）· 同时在线 K（≤ 池容量）· 节奏/重试——客户参数 |
| 触发 | **聊天框自然语言**（小批量 @全员/@角色；大批量 @问卷调度助手） |
| 并发正确性 | 1 角色 = 1 独立部门（沙盒并发基石——**组织架构不动**） |
| 产品叙事 | 用户对话 → 调度助手接管（水位/重试/进度）→ 用户聊天流看进度 |

## 二、产品形态（用户视角一条线）

```
用户在部门聊天框
  ├─ 小批量（10-50 ≤ 池）：@全员/@角色 「请大家填写问卷」
  │    —— 现有机制（seed 已建「问卷调研」部门——@全员 全员响应——各自沙盒并发）
  └─ 大批量（100-1000）：「@问卷助手 让 1000 人填问卷，同时 30 人」
       ① 助手解析意图（总量/并发/问卷链接——自然语言）
       ② 调调度器工具（start——水位派单——不是 @全员——池满等）
       ③ 聊天流回进度：「已完成 320/1000 · 失败 2 · 重试中…」
       ④ 用户可续：「重跑失败的」
```

**心智统一**：小批/大批都是「跟 AI 说话」——角色池、批次、沙盒、
并发对用户不可见——**launch API / 运行器脚本 = 工程面**（调试/测试/
平台 owner 自用——不宣传——不修正使用方式）。

## 三、架构设计

### 3.1 角色供给（seed 升级）

- `seed-survey-agents.mjs --count=1000 --matrix=10x10x10`
- 人设矩阵：行业（10）× 职级（10）× 性格/态度（10）——prompt 模板化
  （稳定句式——指令遵循——现有 10 人设 prompt 为模板样本）
- 命名规约：`问卷-{行业}-{职级}-{性格}-001`——**管理面分区过滤的前置**
- 每个角色：独立部门（沙盒）+ agent（`department_id`=角色部门）+ 入「问卷调研」hub
- 批建事务（每 50 一批——进度可见）

### 3.2 调度器（Campaign——服务端组件——核心新增）

**DB**：
```sql
campaigns(id, app_id, total, concurrency, url, status, failed_count, created_at, ...)
campaign_runs(campaign_id, agent_id, status, attempts, started_at, finished_at, error)
```

**API（agent 工具面——替代 launch 硬编码；launch 保留=调试兼容）**：
```
POST /api/survey/campaigns          { total, concurrency, url } → 启动
GET  /api/survey/campaigns/:id      → status/进度/在线/失败清单
POST /api/survey/campaigns/:id/retry → 失败清单重跑
POST /api/survey/campaigns/:id/cancel
```

**水位循环（服务端——事件驱动——不是脚本轮询）**：
```
① 补派：active < concurrency → 从池取未派角色 → 部门消息 @角色（现有触发面）
② 完成：survey:submitted（WS 事件）或 survey-result.json（文件事件）→ 记账
③ 超时：180s 未完成 → attempts+1 → retry 内重派 → 失败清单（attempts 耗尽）
④ 收尾：completed + failed >= total → status=done → 批回收（见 3.6-P1-2）
⑤ 事件：每完成/失败 → 聊天流消息（部门——进度可见）
```

### 3.3 调度助手 agent（产品入口）

- seed 建「问卷调度」部门 + 调度助手 agent（`is_dispatcher` 标识/role_label）
- system_prompt 引导：解析用户意图 → 调调度器工具（start/status/retry）→
  聊天流汇报进度（简明——「已完成 N/M · 失败 K」）→ 失败清单与重试对话
- 工具面：调度器 API 注册为 agent 工具（与 plan_tasks 同构——**产品已有
  agent 调用工具机制**——复用）

### 3.4 sandbox 管理（问题清单——按严重度——解法）

| # | 问题 | 1000 冲击 | 修法 |
| --- | --- | --- | --- |
| P0-1 | 无等待队列（池满 queue:rejected 抛错） | 必然拒绝——角色失败 | exec 排队（池空位即跑——超时可见——busy 豁免保持） |
| P0-2 | 派单硬编码 BATCH=3/10s | 1000 = 55 分钟纯派单 | 调度器水位（池容量感知——替代批控） |
| P1-1 | 任务级保护缺位（LLM 间隙容器被 LRU 驱逐） | 长任务回收 | 会话活跃容器豁免（请求级标记） |
| P1-2 | 批收尾缺失（idle 10min 才 stop） | 1000 容器空转 10min | campaign 完成 → 批量 stop（省资源/可观测） |
| P1-3 | 统计页逐来源列表爆 | 1000 行——统计意义丢 | 聚合分布（年龄/行业/评分直方图——S5） |
| P2 | 容器启动风暴/人设供给/metrics 告警/LLM 上游并发/DB 批建 | 各按需 | 预热池/seed 升级/告警/试点实测/批事务 |

**三层并发闸（取最小 = 有效并发）**：沙盒池容器数（物理内存）·
LLM 上游（**试点 100 实测——多 key 轮换备选**）· 客户 --concurrency。

### 3.5 统计与产出（1000 的统计意义）

- 统计页聚合：分布（年龄/行业/评分直方图）+ 完成率/失败率/耗时
- summary 报告：campaign 完成 → 汇总（分布/失败清单/耗时）
- 聊天流进度（3.2-⑤）+ 统计页（运营/交付报告面）

### 3.6 组织架构（决策——骨架不动 + 管理面治理）

- **不动**：1 角色 = 1 部门 = 1 沙盒（并发正确性——共享部门需 per-agent
  沙盒=阶段 4 大改——**判负**）
- **不做**：1000 角色部门挂组织树（非组织语义——聚合成本 > 收益——**判负**）
- **做**：命名规约 + 部门/agent 列表分区过滤（`问卷-` 前缀——1000 实体可管理）
- **真人组织 1000**（不同语境）：多部门 + 组织树递归——**独立波次**
  （真实客户需求触发——与本方案不耦合）

## 六、风险

- LLM 上游限流（100 试点实测——多 key 轮换备选）
- 人设 prompt 漂移（模板化——指令遵循测试——100 试点观察）
- 问卷版本变化（版本号进 prompt——问卷变更重 seed）
- 成本（1000 × ~8 次 LLM——试点测量后承诺）
- 沙盒泄漏（reconcile/驱逐已备——监控池使用率——S4 批收尾缓解）
