# Webhook Agent 对接体验优化计划

> 目标：围绕**用户如何对接、测试、调试 Webhook Agent 的收发**，补齐对接体验与关键技术能力。
> 现状基线：入站端点（HMAC 签名 + replay 防护 + 指数退避重试 + 调用日志）已有；出站回调为死配置（诚实标注预留）。
> 验收方法：agent-browser 红→绿逐项验证 + curl/示例代码实测 + 全量回归（框架 1936 + app 81 + tsc）。

## 一、对接体验（外部系统接入环节）— ✅ 目标 5/5

用户接入外部系统时看到的是「相对路径 `/api/webhook/{id}` + 三个头名」——真实对接需要完整 URL、请求格式、签名算法、可直接跑的示例。

- [ ] **H1. 完整 URL 展示 + 复制** — 入站端点显示 `http://localhost:3000/api/webhook/{id}`（完整绝对地址，含 host），复制按钮复制完整 URL——外部系统可直接使用（当前复制相对路径，对接时还需自己拼 host）
- [ ] **H2. 对接指南面板（含签名示例）** — AgentDetail 新增「🔗 对接指南」折叠面板，展示：
  - 请求格式表：`content`（必填，消息内容）、`conversation_id`（可选，会话 ID）、`key`（可选，透传）
  - **curl 示例**（无 secret 版本 + 有 secret 版本**自动带当前 Secret 的 HMAC 签名**——复制即用）
  - Node.js fetch 示例（自动签名代码段，含 crypto 签名 + 三头）
  - 每个示例配「复制」按钮（ctx.browser.copyText）
- [ ] **H3. 签名验证失败可读化** — 401/403 错误响应带明确原因（`Missing X-Signature` / `Invalid signature` / `Replay detected`），UI 测试结果直接展示服务端错误消息（当前 `(d as any).error` 已有——补 curl 示例中的错误处理展示）
- [ ] **H4. 生成随机 Secret** — Secret 输入旁加「🎲 生成」按钮（`crypto.randomUUID()` 去横线 32 hex）——替代用户手敲；点击后填充 + 提示已复制
- [ ] **H5. 出站回调诚实裁剪复核** — `webhook_url` 从「可输入 URL + 预留标注」改为只读「📡 出站回调：规划中（当前版本仅入站）」——避免用户配置后期待推送（CS-05：不静默降级）；NewAgent 同步移除该输入框

## 二、测试体验（收发验证环节）— ✅ 目标 3/3

当前「发送测试请求」发送固定文本「测试消息：验证 Webhook 机器人可用」——无法测试不同提示词；结果只显示 reply 一行。

- [ ] **T1. 测试消息自定义** — 测试区域加内容输入框（默认「测试消息：验证 Webhook 机器人可用」），可输入自定义消息测试不同 prompt/工具
- [ ] **T2. 测试结果完整展示** — 应答区显示：HTTP 状态码 + 耗时（ms）+ 回复内容；失败时展示服务端 error 原文 + 状态码——一次测试可判断「通不通/为什么不通」
- [ ] **T3. 测试后自动滚到日志** — 测试完成自动刷新日志列表（已有）→ 新日志条目高亮/置顶标记（便于确认本次请求落库）

## 三、调试/观察体验（日志环节）— ✅ 目标 3/3

`webhook_logs` 表已存 `request_body`/`response_body`/`response_status`/`elapsed_ms`/`success`——但 UI 只显示「HTTP 200 + 时间 + 耗时」，调试外部系统对接问题时看不到请求/响应内容。

- [ ] **D1. 日志条目可展开** — 点击日志条目展开：请求体全文（pre 格式化 JSON）+ 响应体全文 + 状态码 + 耗时 + 时间——对接调试的核心证据
- [ ] **D2. 日志过滤** — 全部/成功/失败 三态切换（失败条目红色标记「HTTP 4xx」）——快速定位对接失败
- [ ] **D3. 日志自动清理策略** — 后端按 agent 保留最近 500 条（超量删除最旧）——防无限增长

## 四、技术要点（后端能力）— 目标 3/4 + 1 决策

- [ ] **B1. conversation_id 会话记忆** — 同 conversation_id 的多轮调用保持上下文（服务端按 conversation_id 缓存最近 N 轮消息，Redis/SQL 持久化）——外部系统多轮对话的基础；无 conversation_id 时保持单轮（兼容）
- [ ] **B2. 入站端点限流豁免** — 外部系统高频调用（电商下单通知、客服接入）会被全局 rateLimit（100/60s）429 拦截——入站 webhook 端点从全局限流豁免或独立阈值（如 300/60s），文档说明
- [ ] **B3. 请求体大小限制** — 入站 body 上限（如 64KB）防滥用；超限返回 413 明确错误
- [ ] **B4. 出站回调决策**（评估项，不改代码）— 记录决策：① 保持裁剪（入站定位）+ UI 只读标注（H5）；② 或实现最小出站（AI 工具 `webhook_send` 推送结果到 webhook_url）——评估工作量/收益后登记决策到结果文件，不静默

## 验收清单（agent-browser）

```
对接环节：open AgentDetail(webhook) → 完整 URL 可见可复制 → 对接指南含 curl(带签名)/Node 示例 → 生成 Secret → 保存后 curl 示例签名仍有效
测试环节：自定义消息输入 → 发送 → 状态码/耗时/回复展示 → 日志新增
调试环节：展开日志看请求/响应体 → 失败过滤 → 制造 401（错误 secret）→ 错误消息可读
后端：多轮 conversation_id（两次调用 AI 记得上文）→ 高频 curl（>100 次无 429）→ 大 body 413
```

## 优先级

| 优先级 | 项 | 理由 |
|--------|-----|------|
| P0 | H1 H2 H4 T1 T2 D1 | 对接测试的核心体验缺口（完整 URL/示例代码/自定义测试/日志详情） |
| P1 | H3 H5 D2 B2 B3 | 失败可读化 + 防误导 + 限流豁免（真实对接必踩） |
| P2 | T3 D3 B1 B4 | 会话记忆（新能力）/ 决策项 / 优化项 |

> 原则：所有 UI 改动遵守 AGENTS.md §5.4（portal/usePopup）、§5.6（样式原语、wf-nums）、浏览器环境纪律（ctx.browser）；新增能力写测试；诚实裁剪（不支持的明确标注）。
