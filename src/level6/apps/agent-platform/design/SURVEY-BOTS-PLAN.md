## 二、产品形态（用户视角一条线——不变）

```
用户在部门聊天框
  ├─ 小批量（10-50 ≤ 池）：@全员/@角色 「请大家填写问卷」
  └─ 大批量（50-100）：「@问卷助手 让 100 人填问卷，同时 10 人」
       ① 助手解析意图（总量/并发/链接）→ 调调度器工具
       ② 水位派单（不是 @全员）→ 聊天流进度「52/100 · 失败 2 · 重试中…」
       ③ 用户可续：「重跑失败的」
```

**心智统一**：小批/大批都是「跟 AI 说话」——角色池、批次、沙盒、
并发对用户不可见——launch API / 运行器 = 工程面（不宣传不修正）。

## 三、实测校准的性能模型（v2 核心修订）

### 3.0 实测数据（2027-09——全部真实验证）

| 参数 | 实测值 | 来源 |
| --- | --- | --- |
| 单角色端到端 | **45s**（读消息→agent-browser 开页→填 5 题→提交→写结果→完成信号） | 单角色 campaign |
| 试点 100 | **5.3 分钟**（concurrency=10——100/100、0 失败） | S7 试点 |
| 容器内存 | **306MB**（问卷页——chromium 满载） | docker stats |
| 容器启动 | **<1s**（docker run 秒回） | 实测 |
| 任务内 exec 链 | 每角色 ~10-15 次工具调用 | 压测 800 次（68ms/次） |
| LLM 调用 | ~8-10 次/角色（快照→决策→工具） | 观察 |

### 3.0.1 性能模型（定参版）

```
100 交付 = 100 × 45s / K 并发（K = min(并发上限 10, 池容量, LLM 上游闸))
  K=10 → 实测 5.3 分钟（试点 100——不预估——已实测）
```

**关键结论**：试点 100 @10 已实测 100/100 · 0 失败——**性能模型不需要外推**
（v2 的 1000 外推随规模判负一起失效——不再需要 K=20 翻倍杠杆）。

**并发闸定参（2027-09 用户决策）**：上限 **10**（服务层 `clampConcurrency`
单一实现源——API/工具超限一律夹紧）——依据：10 并发实测无限流 + 0 失败；
20 未实测——判负不做（不冒 LLM 上游限流风险——多 key 备选也不做——无场景）。
池容量视角余量充足：10 × 512MB = 5120MB ≤ 10240MB 预算（50%——可双 campaign 并行）。
