# 客户演示增强计划（问卷场景复盘 → 能力增强）

> 复盘：客户演示「10 个机器人填写问卷」全过程的真实问题 → 定义需要增强的能力 → 任务清单（红→绿）。
> 前置能力已就绪：三层模型/组织层级/沙盒可观测性（事件日志+诊断）/产物验证/审批流。

---

## 一、演示复盘：遇到的问题清单

| # | 问题 | 客户感知 | 根因 | 现状 |
|---|------|---------|------|------|
| 1 | **一键填写分批 3 个 3 个**（45s×4 批） | 以为卡住/「机制是什么」 | 旧版防池耗尽的保守分批，无进度反馈 | ✅ 改为部门 @全员 自然路径（已修） |
| 2 | **`/api/departments` 接口卡住** | 页面转圈 | 10 角色并发 AI 执行占满 pg 连接池（30）无 acquire 超时 → 无限排队 | ✅ 池 50 + acquireTimeout + 事件独立池（已修） |
| 3 | **角色「只回复收到不干活」**（研发大刘两次） | 为什么没填？ | LLM 惰性：看到旧结果认为完成/只回复计划不执行 | ✅ 提示词执行纪律 + 新旧产物验证标记（已修） |
| 4 | **旧结果被标「已验证」** | 明明没重填却显示已验证 | 验证不区分文件新旧 | ✅ stale 标记（已修） |
| 5 | **重复派单语义不清** | 第二次点一键没反应 | 消息无「新任务覆盖」语义 | ✅ 消息强化（已修） |
| 6 | **问卷 URL 用 localhost**（容器内连不上宿主） | AI 第一次失败重试 | 消息里给了容器不可达地址 | ⚠️ 靠提示词纪律纠正——需**地址注入机制** |
| 7 | **进度对客户不可见** | 「不知道进行到哪、还要多久」 | 只有统计页提交数（WS 内存态），**无任务级状态视图** | ❌ **待增强（核心）** |
| 8 | **AI 卡住/失败无自动恢复** | 部分角色没填完就结束 | 无工具调用/执行失败 → 仅标记，不自动重试 | ❌ **待增强** |
| 9 | **并发高峰资源不可见** | 沙盒页看不出「10 个同时在跑什么」 | 有诊断（单沙盒），**无聚合视图**（哪些在跑/排队/等待） | ❌ **待增强** |

**核心洞察**：已修的都是「点状问题」（连接池/验证/提示词）；**客户真正需要的是「整体可见性 + 可靠性」**——知道任务进展、AI 没干活能被抓住并自动恢复。

## 二、增强方案（按客户价值排序）

### P1 任务执行总览（执行面板）——「客户看得到进度」

**目标**：一次 @全员 派单 = 一个「执行任务」——10 个角色的实时状态一目了然。

```
问卷调研部门（或独立「任务」入口）
┌─────────────────────────────────────────────┐
│ 执行任务：问卷填写（10 角色）                  │
│ 财务小王  ✅ 已完成 18:33:24（提交 #xxx）      │
│ 市场小李  ▶ 执行中 4 分 12 秒（浏览器填写中）   │
│ 研发大刘  ⏳ 等待中 / 🔁 重试中（无工具调用）    │
│ 实习生阿泽 ⚠️ 失败：地址不可达（已自动重试）      │
│ 进度：7/10 完成 · 预计剩余 1-2 分钟             │
└─────────────────────────────────────────────┘
```

**数据源（全部已有——聚合即可）**：
- `sandbox_events`（exec_start/exec_done/timeout/error——执行链路）
- `agent_logs`（执行记录 success/tokens）
- 产物文件 mtime（survey-result.json 更新 = 完成）
- `sandboxes`（runningExecs 实时——诊断 API 已暴露）

**实现**：
- `GET /api/tasks/:deptId/executions`（或 `GET /api/departments/:id/executions`）：聚合各部门成员的最近执行状态
  - 每个成员：最后消息时间 / 执行中（runningExecs）/ 最近事件（exec_timeout/error）/ 产物新旧 / 状态推导（idle/working/stalled/failed/done）
- UI：问卷调研部门页顶部「执行面板」卡片（或独立 /tasks 页）——**演示时客户一眼看到 10 个角色的状态**；统计页增强（复用 WS 提交 + 执行状态）

### P2 AI 执行可靠性（自动恢复）——「角色没干活能被抓住」

**无工具调用检测 + 自动重试**：
- AI 回复完成但**本轮 0 次工具调用**（agent_logs.steps_count=0 或运行期检测）→ 判定「惰性回复」→ **自动重新派发一次**（消息附加「你上一轮未实际执行——必须调用工具，这是自动重试」）
- 重试仍 0 工具 → 标记「需要人工介入」（任务面板显示）

**产物未更新自动重试**：
- 验证标记含 stale/missing 且 AI 声称产物 → **自动重发一次**（而非仅标记）——研发大刘场景自动恢复

**实现**：
- chat.ts 完成钩子：0 工具调用 / 产物 stale → 触发 `retryTask(agentId, deptId, 原因)`（有限重试 1-2 次，防循环）
- 任务面板显示重试次数与原因

### P3 外部地址注入（问卷 URL 自动正确）

**问题**：消息里 localhost 容器不可达——AI 靠提示词纪律纠正（慢/易错）。

**方案**：`SURVEY_URL` env 已支持——**增强为服务启动时自动推导可用地址**：
- 检测宿主 IP（非 localhost）→ 注入 `PUBLIC_BASE_URL`（若未配置）
- 消息模板/提示词统一用 `PUBLIC_BASE_URL`（宿主 IP）——容器内用 `host.docker.internal` 访问（提示词已有）
- **seed/消息构造时校验地址可达性**（容器内 curl 探测失败 → 日志提示）

### P4 并发高峰聚合视图（沙盒页「执行中任务」汇总）

- Sandboxes 页顶部加聚合条：`执行中 N · 排队 M · 等待容器启动 K`
- 数据：runningExecs 聚合（executor 已有）+ 池状态
- 客户演示并发时可看到「10 个环境同时在干活」

### P5 演示一条龙脚本（survey-demo.mjs）

- seed（角色+部门+问卷调研）→ 发 @全员 → 监控任务面板 → 汇总——单命令完成
- 客户演示流畅（不用记多个脚本）

### P6 运维增强（低成本）

- pg 连接池活跃数 → /api/metrics（池耗尽预警——本次事故的预防）
- 沙盒事件聚合 API（per dept 最近事件流——任务面板数据源）

## 五、决策记录

1. **任务面板基于既有数据聚合**（sandbox_events + runningExecs + 产物 mtime）——零新状态源，可观测性投资的直接回报
2. **自动重试上限 1-2 次**——AI 不可靠是常态，但防无限循环（重试风暴）
3. **惰性回复判定 = 本轮 0 工具调用**——简单可靠（vs 语义分析）
4. **地址注入走 PUBLIC_BASE_URL 推导**——不硬编码 IP（部署环境无关）
5. **P1 优先**（客户可见性）> P2（可靠性）> P3-P5——演示说服力的直接排序
